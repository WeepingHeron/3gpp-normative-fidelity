# 01. 연구 계획

## 1. 문제 정의

3GPP 기술규격은 `shall`, `should`, `may`, `can` 등을 단순한 문체가 아니라 요구, 권고, 허용, 능력을 구분하는 규범적 표현으로 사용한다. LLM이 이 문장을 한국어로 요약하거나 설명하면 다음 오류가 생길 수 있다.

- 요구(`shall`)를 가능(`can`)으로 약화
- 권고(`should`)를 요구(`shall`)처럼 강화
- 금지(`shall not`)의 부정 누락
- 요구의 실행 주체 바꾸기
- `if / when / unless` 조건과 예외 누락
- 원문에 없는 의무나 예외 추가

이러한 오류는 단순한 번역 품질 이슈가 아니라 표준 요구사항의 공학적 의미를 바꾸는 오류다.

## 2. 제안 방법

C2는 응답 생성 전에 원문을 다음 계약으로 구조화한다.

```json
{
  "actor": "UE",
  "condition": "...",
  "modality": "shall_not",
  "action": "...",
  "exception": null,
  "source_spec": "3GPP TS 23.501",
  "source_version": "pinned before collection",
  "source_clause": "..."
}
```

응답 생성기는 이 필드를 바꾸거나 추축하지 못하며, 추출이 불완전하면 설명을 보류하고 원문을 제시하도록 설계한다.

## 3. 가설

- **H1:** C0보다 C1의 규범 유형 정확도가 높을 것이다.
- **H2:** C1보다 C2의 규범 유형·부정·행위자·조건 완전 보존율이 높을 것이다.
- **H3:** C2는 C1보다 unsupported addition rate가 낮을 것이다.
- **H4:** C2의 정확도 향상이 응답 시간·토큰 비용 증가보다 실무적으로 의미 있을 것이다.

H4는 비용과 지연을 실제로 기록할 수 있을 때만 검증한다. 데이터가 없으면 `not_evaluated`로 남긴다.

## 4. 범위

### 필수 범위

- ETSI TS 123 501·TS 124 501(V18.12.0, Release 18)의 고정 PDF
- 영문 원문과 한국어 질문·설명
- 6개 규범 카테고리, 총 72개 사례
- 하나의 주 모델과 고정된 파라미터
- C0/C1/C2 paired evaluation

### 제외 범위

- 3GPP 전체 문서 검색 시스템 구축
- 모델 파인튜닝
- 다중 Agent orchestration
- Release 간 차이 추적
- 표·그림·ASN.1 멀티모달 추출
- 통신 네트워크 성능이나 적합성 입증

## 5. 재현성 원칙

- 표준 번호, Release, 버전, 다운로드 URL, 파일 SHA-256을 기록한다.
- 모델 ID, 실행일, temperature, seed 지원 여부, prompt version을 기록한다.
- C0/C1/C2의 질문 문구와 출력 형식을 조건 외에는 동일하게 유지한다.
- 실행 전에 데이터셋과 prompt를 동결하고 해시를 기록한다.
- 예상과 다른 결과도 제외하지 않고 보고한다.

## 7. 중단 기준

다음 중 하나가 발생하면 72개로 확장하지 않고 pilot을 수정한다.

- 동일 응답을 다른 채점 시점에 다르게 판정함
- C1과 C2의 입력 정보량이 의도치 않게 다름
- gold label이 원문에서 직접 확인되지 않음
- 응답 형식이 안정적으로 파싱되지 않음
- 주 지표가 모두 수작업 주관 평가에만 의존함
