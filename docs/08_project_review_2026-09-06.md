## 2. 제출 전 우선 보완

### 높은 우선순위 — C2 입력과 평가자 정체를 정확하게 기술

`experiments/run_pilot.mjs:188`은 데이터 행을 그대로 prompt 변수로 전달하고 modal class를 normative type으로 변환한다. `experiments/prompts/c2_v2.md`에는 actor·condition·normative_type·polarity·action·exception이 들어간다. 이 필드들은 평가에 사용하는 정답 구조와 같은 출처다. 자동 추출기를 평가하는 구현은 현재 비교에 포함되지 않는다.

따라서 이 설계는 **정답 구조를 제공하는 oracle structured condition의 효과**를 확인하는 실험으로 유효하다. 구조화 표현의 효과와 정답 해석을 추가 제공한 효과를 현재 실험만으로 분리할 수는 없다. C2 modal 정확도 100% 역시 정답 modal이 입력에 들어가는 조건이라는 설명이 필요하다. C1은 상세 보존 지시까지 갖춘 oracle-source baseline이므로 일반적인 vanilla RAG로 부르면 실제 통제 조건보다 넓게 들린다.

논문 두 버전은 평가자를 단순히 ‘동일 평가자’로 기술하며 ‘사람이 만든 정답 구조’라는 표현도 사용한다. 실제 기록이 Codex 평가라면 `Codex 기반 라벨 초안과 의미 평가, 독립 통신 전문가 검증 미실시`처럼 역할을 밝혀야 한다. 사람이 검수한 범위가 있다면 그 범위와 기록을 별도로 제시한다. 동일 도구를 하루 뒤 다시 실행한 κ는 인간 평가자 내 신뢰도나 독립 인간 평가자 간 신뢰도를 입증하지 않는다. 평가 모델·세션·입력·rubric 기록도 보강할 필요가 있다.

### 높은 우선순위 — 모호한 gold 3건과 통계 민감도를 함께 보고

| 분석 | C1 | C2 | 차이 | exact McNemar 양측 p |
|---|---:|---:|---:|---:|
| 동결 72건 | 65/72 | 72/72 | +9.72%p | 0.015625 |
| 모호한 3건 제외 | 65/69 | 69/69 | +5.80%p | 0.125 |

현재 sensitivity 파일은 비율만 계산하고 검정까지 계산하지 않는다. 이번에 독립 재계산한 p=0.125는 ‘개선 방향 유지’와 ‘유의성 유지’를 구분해야 함을 보여준다. 이것이 효과가 없다는 증명은 아니지만, 강한 효과 주장에는 제약이 된다. 동결 72건을 보존하고 69건 분석을 민감도 분석으로 병기한다.

특히 `MAIN-CAN-008`의 원문은 “Before security can be activated, the AMF and the UE need to establish a 5G NAS security context.”이고 질문도 AMF와 UE의 전제조건을 묻는다. C1은 보안 활성화 전에 두 주체가 context를 수립해야 한다고 설명했으나 동결된 `actor=security`, `modal=can` 기준에서는 실패다. 질문과 원문 전체에 비추어 수용 가능한 답일 가능성이 있으므로 이 건은 단순 모델 오류로 단정하기 어렵다. `MAIN-CAN-004`의 구현·배포 책임과 `MAIN-SD-002`의 종속절 should 범위도 함께 검토해야 한다.

권장 검토 순서는 C1 실패 7건과 같은 사례의 C2 답변, modal 불일치 9건, 그리고 성공 표본이다. 문제 사례만 재검토한 표본으로 전체 신뢰도를 산출하지 않는다. 가능하면 C1/C2 전체 144건을 독립적으로 평가하고, 최소한 실패 전수와 사전 무작위 성공 표본의 제한된 감사임을 명시한다.

### 높은 우선순위 — ‘실행 전 지정’ 표현의 근거가 부족

Markdown 초안 75행과 DOCX는 위 3건의 모호성을 ‘모델 실행 전에’ 지정했다고 말한다. 확인한 실행 전 동결 commit `95d8a2c`의 문서·코드·JSON에는 이 3건을 모호성 대상으로 지정한 기록이 없었다. 확인 가능한 최초 gold-scope 기록은 본 실험 후 pass 1 commit `81a4472`(2026-09-03 16:55 KST)이며, 실제 API 실행은 16:35~16:43 KST였다. `NEXT_STEPS.md`의 설명은 ‘delayed pass 2 전에’ 지정했다는 수준이다.

별도 시점 증거가 없다면 `1차 평가 후 발견하여 지연 2차 평가 전에 기록한 gold-scope 모호성`으로 수정하는 것이 타당하다. 데이터·프롬프트 사전 동결과 모호성 사전 지정은 서로 다른 주장이다. 원래 동결 파일을 소급 수정하지 말고 후속 정정 기록을 남긴다.

### 높은 우선순위 — 평가 지표의 대상과 이름이 다름

`experiments/score_run.mjs:40`의 modal_correct는 JSON의 normative_type을 비교한다. 그러나 `experiments/scoring_v1.md`는 설명의 규범 유형을 평가한다고 정의한다. 실제로 C1의 9건은 JSON modal이 틀려도 한국어 설명 완전 보존은 성공이다. 따라서 56/72와 65/72 자체가 산술 모순은 아니지만, 둘을 같은 자연어 의미 지표로 설명하면 모순처럼 보인다.

기존 기록을 유지하면서 `JSON modal label accuracy`와 `Korean explanation preservation`을 명시적으로 분리한다. 자연어 modal accuracy를 별도 보고하려면 별도 판정이 필요하며 JSON 점수를 그대로 재명명해서는 안 된다. 추가로 `JSON–설명 일관성`을 진단 지표로 둘 수 있다. 부정·강도가 묶인 polarity_preserved도 순수 부정 정확도와 구분해야 한다.

### 중간 우선순위 — 인용과 비용의 해석

C1/C2의 citation은 입력에 제공된 spec·version·clause를 복사하는 검사다. 100%는 출처 식별자 복사 정확도이며 근거 함의 검증이나 검색 성능이 아니다.

원본 usage 합계는 C1 입력 41,746·출력 11,569·총 53,315 tokens, C2 입력 47,971·출력 11,223·총 59,194 tokens다. C2의 입력은 약 14.9%, 전체 token은 약 11.0% 증가했다. 추가 API 없이 계산 가능한 보조 결과다. 다만 자동 구조 추출 비용이나 라벨 구축 인건비를 포함하지 않으므로 end-to-end 비용 우위로 주장하지 않는다. 현재 runner는 요청별 완료 시각·경과 시간을 직접 저장하지 않아 정밀한 지연 비교는 별도 계측이 필요하다. manifest의 약 $0.25는 당시 요율을 사용한 추정치다.

### 중간 우선순위 — 재현성과 관리 문서

- README는 아직 첫 pilot 준비 상태다. NEXT_STEPS의 원고 체크, modal별 source 균형 6+6 문구도 현재 데이터와 맞춰야 한다. 실제 should는 4+8, should_not은 8+4이며 예외는 난도 규약에 기록돼 있다.
- 72개 문장은 44개 source clause에서 나왔고 한 clause에 8개가 들어간다. 문장 간 독립성이 완벽하지 않을 수 있으므로 source·clause별 분포를 공개하고 필요하면 clause 단위 cluster bootstrap을 보조 분석으로 사용한다. 현재 신뢰구간을 3GPP 전체 모집단의 대표성으로 설명하지 않는다.
- annotate 스크립트는 특정 review ID의 판정을 하드코딩하고 미기재 행을 성공 처리한다. 이는 저장된 리뷰 재현용이며 새 응답 채점기로 재사용하면 위험하다. 입력 hash·run ID·review mapping을 검사하고 새 run에는 새 리뷰 기록을 요구하도록 개선한다.
- 단일 문서로 설치·오프라인 검증·집계 재생성 절차를 정리한다. freeze·분석 스크립트는 일부 출력 파일을 덮어쓰므로 검증과 생성 명령을 구분한다.
- 원문 PDF 재배포 권한은 프로젝트 안에서 미확정이다. 공개 패키지는 코드·메타데이터·공식 URL·hash 중심으로 설계하고, 원문·발췌문 공개 범위는 확인 후 정한다.
- DOCX와 Markdown은 별개 편집본이며 내용이 완전히 같지 않다. 현재 승인본과 생성 경로를 지정하고 제출 산출물 hash를 별도로 남기는 편이 좋다.

## 3. 남은 기간의 확장 선택

기간은 구현·채점 작업량에 대한 제안이며 확약이 아니다. 사람 검토자 확보 시간은 별도다. 추가 실험 전 데이터·프롬프트·지표·실패 처리·중단 시점을 별도 run으로 동결한다. 유의한 결과를 얻을 때까지 사례를 추가하거나 모델을 고르지 않는다.

| 확장 | 무엇을 확인하는가 | 예상 작업 | 권장 |
|---|---|---|---|
| 독립 검토 + 지표·민감도 정리 | 현재 결론이 올바른지 | 1~3일, 검토자 일정 별도 | 제출 전 최우선 |
| 자동 구조 추출 C3 | 정답 구조 없이도 효과가 남는지 | 구현·실행·검토 2~4일 | 추가 실험 1순위 |
| modal만 제공하는 C1+M | 완전 구조의 추가 효과인지, modal 정답 힌트 효과인지 | 1~2일과 채점 | 원인 분리에 유용 |
| 다른 모델 1개에서 C1/C2 | 모델 의존성이 어느 정도인지 | 1~3일과 채점 | 여력이 있을 때 |
| 새로운 clause 중심 외부 표본 | 현 문장·문체를 넘어 재현되는지 | 3~5일 이상, 새 gold 필요 | 제출 후 우선 |
| 실제 retrieval 파이프라인 | 검색 실패까지 포함한 성능 | 통합·평가 부담 큼 | 후속 졸업논문 확장 |

**추천하는 C3 설계:** `원문 → 자동 actor/condition/modal/polarity/action/exception 추출 → 한국어 설명`의 두 단계를 분리한다. 추출기에는 gold 필드나 gold_summary_ko를 전달하지 않고 출력과 실패를 전부 저장한다. 기존 C1, C2-oracle와 비교해 추출 정확도와 최종 설명 정확도를 따로 보고한다. 같은 72건을 사용하면 통제 비교는 가능하지만 새 표본에 대한 일반화 증거는 되지 않는다. 별도 개발 표본에서만 추출 prompt를 조정한다.

전체 72건이라면 추출 72회+생성 72회로 144회가 추가된다. 시간이 부족하면 결과를 보기 전에 source·modal을 고려한 24~36건을 정하고 탐색적 결과로 제한한다. 실패 7건만 선택해 전체 개선율처럼 보고하지 않는다. 보류를 허용하면 보류를 정확한 설명으로 채점하지 말고 coverage와 답변한 사례의 오류율을 함께 보고한다.

**C1+M 설계:** C1에 gold normative_type/polarity만 추가하고 나머지 조건은 유지한다. 72회로 full C2가 modal 힌트 이상의 이득을 주는지 볼 수 있다. 이것도 oracle ablation이며 자동화 타당성을 검증하는 C3와 목적이 다르다. 제한된 일정에서는 C3와 C1+M 중 하나를 선택한다.

장기적으로는 조건·예외를 인위적으로 삭제하거나 modal을 바꾼 구조를 입력해 오류 전파를 측정하는 연구가 잘 연결된다. 인위적 교란 성능은 실제 자연 오류율과 분리한다. 이후 다른 Release, 여러 clause가 필요한 질문, 실제 검색으로 넓히되 각각의 실패 원인을 분리해 측정하는 편이 연구 기여가 명확하다.

| [DeepSpecs](https://aclanthology.org/2026.findings-acl.1343/) | 교차참조와 버전 변화 기반 표준 QA | 검색을 통제한 생성 의미 보존에 초점 |
| [HL-Trans, 2026-07-02](https://link.springer.com/article/10.1007/s10506-026-09529-2) | 법률 번역에서 계층적 제약과 deontic modality 보존 | 3GPP·한국어·modal/행위자/조건/예외 단위 평가 |

HL-Trans는 출판사 공개 초록까지만 확인했다. 중·영·일 법률 번역에서 규범 강도 보존을 다루므로 ‘구조화 제약으로 규범 의미를 보존한다’는 넓은 아이디어는 독창성 주장으로 부족하다. 한국어 3GPP를 똑같이 평가한 연구가 없다고 단정하지 않고, 확인한 문헌과 직접 일치하지 않는 평가 범위를 제시한다.

권장 기여 문장은 `고정된 3GPP 영문 문장의 한국어 설명에서 규범 요소별 오류를 분석하고, 원문 단독·정답 구조·자동 추출 구조의 차이를 통제 비교한다`이다. 마지막 자동 추출 부분은 실제 확장 실험을 완료한 경우에만 넣는다.

## 5. 제출까지의 제안 일정

[한국정보처리학회 공식 공지 목록](https://www.manuscriptlink.com/society/kips/homepage)에서 ACK 2026 모집 마감 제목이 9/16(수) 23:59로 표시됨을 확인했다. 9/6 기준 약 10일이며 상세 모집 페이지 본문은 이번 도구 추출에서 충분히 읽히지 않았다. 제출 형식 세부사항은 최종 제출 화면·공식 양식을 다시 확인한다.

- **9/6~8:** 평가자·C2 입력·지표·사전 지정 문구와 sensitivity p를 정리하고 독립 검토를 진행한다. 리뷰 요청 전 실패·성공 표본과 rubric을 준비한다.
- **9/8~11:** 여력이 있으면 C3 또는 C1+M 하나만 별도 동결해 수행한다. 독립 평가와 원고 수정을 방해하면 확장을 중단한다.
- **9/12~14:** 분석을 닫고 원고·표·그림에 반영한다. C3가 C1보다 나쁘더라도 추출 오류가 oracle 이득을 상쇄한다는 결과로 보고한다.
- **9/15:** 제출 파일의 한글·페이지·인용·수치를 실제 제출 환경에서 최종 검수한다.
- **9/16:** 마감보다 여유 있게 제출한다.

## 6. 이번 검토의 검증 범위와 산출물

기존 연구 데이터·코드·논문은 수정하지 않았다. 재계산용 `tools/review_project_20260906.py`와 이 보고서만 추가했다. 검증 스크립트는 API 호출이나 파일 쓰기를 하지 않는다.

재현 명령:

```bash
python3 tools/verify_main_freeze.py
python3 tools/review_project_20260906.py
```

두 명령 모두 통과했다. original prompt·dataset 18개 및 API output 7개 파일 hash, 216개 pairing, 파생 지표 일관성, 주요 비율·exact McNemar와 token 합계를 확인했다. 별도의 의미 재라벨링이나 API 재실행은 하지 않았다. 원문 PDF 72개 문장의 시각적 재대조, 독립 전문가 검토, 새 모델·자동 추출 실험은 이번 검토에 포함하지 않았다.

기존 DOCX는 번들 LibreOffice 기반 renderer로 2쪽이 생성됐지만 양쪽 페이지에서 한글이 공백·네모로 표시됐다. 원본 XML에는 한글 텍스트가 존재하므로 파일 손상으로 단정할 수 없으며 현재 변환 환경의 글꼴·대체 설정 문제 가능성이 있다. 이번 렌더 결과로 인쇄 품질이나 최종 쪽수를 승인하지 않는다. 한글이 정상 표시되는 제출용 PDF를 만들고 모든 페이지를 다시 확인해야 한다. 원고의 방법·통계 수정과 함께 해결할 제출 전 항목이다.
