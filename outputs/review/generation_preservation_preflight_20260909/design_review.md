# 생성 보존 실험: 실행 전 설계 검토

2026-09-09 · 검토자: 진행 AI · **판정: PASS_WITH_LIMITATIONS / 입력 동결 가능. 미해결 차단 사항 0건.**

이번 검토는 작성자의 설계·코드 재검토이며 별도 AI나 사람 전문가의 독립 검토가 아니다. 실제 모델 응답을 생성하거나 평가하지 않았다. 최초 초안은 draft_snapshot과 draft_snapshot_manifest.json에 원문·해시를 보존했다. 최종 검토 입력과 완료 시각은 design_review.json에 기록한다.

## 설계 적합성

| 항목 | 확인한 근거 | 판단 |
|---|---|---|
| 비교 질문 | 세 조건의 모델·FULL 문맥·대상·질문·출력 schema·상한이 같음 | 추가 생성 지시의 개발 효과 비교에 적합 |
| 기준선 | A0 요청 3종이 직전 FULL/NONE 요청과 정확히 일치함 | 과거 응답은 재사용하지 않고 새로 생성 |
| 개입 | A1은 공통 강도 지시, A2는 동일 A1 뒤에 공통 명제 점검 지시만 추가 | 사례별 평가 정답은 입력되지 않음 |
| 자료 경계 | 평가 필드를 변조해도 요청이 동일함. PDF·원문 페이지 해시와 인용 일치 | 직접 정답 필드 유입 없음. 설계가 과거 오류에 영향을 받았음은 유지 |
| 평가 범위 | 직전 2+4+3개 요구사항과 의미 평가 규칙을 그대로 재사용 | 새로운 결과를 본 뒤 분모·요구사항을 바꾸지 않음 |
| 주 비교 | A2−A0를 주 비교로 고정, 나머지는 보조 비교 | 좋은 조건만 사후 선택하는 통과 판정 금지 |
| 규모·집계 | 3원문×3조건×2회, 조건당 6슬롯 | 반복과 두 평가자를 독립 생성 표본으로 세지 않음 |
| 다음 단계 | 완수·왜곡의 미확정 범위를 포함한 보수적 진행 기준 | 공학적 선별 기준이며 통계적 성공 입증이 아님 |

원문 의미도 제공된 인용과 다시 대조했다. CTX-001의 “each SMF may also have the capability”는 능력 보유의 선택성에 걸리고 대상은 하나의 PDU Session에서 두 UPF를 제어하는 것이다. CTX-002는 기본 저장의 should, SUPI 일치 시 사용과 불일치 삭제, 긴급 등록·eCall의 비휘발성 저장 금지·ME 임시 저장·각 삭제 계기를 구분한다. CTX-003은 NR satellite access와 network may be configured의 문맥에서 should not … unless를 평가한다. 위치정보가 있다는 사실을 자동 의무나 유일한 허용 요건으로 바꾸는 것은 요구하지 않는다. 이 검토는 보관 원문 텍스트를 읽고 기존 PDF 해시를 확인한 것이며 PDF 페이지를 새로 시각 검토했다고 표시하지 않는다.

## 발견 사항과 동결 전 보완

| ID | 초안에서 불완전했던 부분 | 보완 | 상태 |
|---|---|---|---|
| D01 | 18슬롯 실행기와 실행 봉인 절차가 아직 없음 | 전용 실행기, 고정 경로·요청 해시 확인, 전체 슬롯 회계표, 원본 응답·usage·시각과 출력 봉인 구현 | 해결 |
| D02 | 두 평가자 모두 기존 결과를 모른다는 것으로 읽힐 수 있는 protocol 표현 | 진행 AI의 설계·과거 결과 사전 지식을 명시하고 새 AI 문맥과 구분 | 해결 |
| D03 | 전달 실패의 NOT_ASSESSABLE를 개별 판정 필드에서 표현하는 규칙 부족 | 정상 의미 null과 별도 문자열로 구분. 전달 실패의 완수는 0, 미요청·통신 결과 미상은 NOT_OBSERVED | 해결 |
| D04 | 문장 수·메타·인용 진단과 의미 점수의 관계가 충분히 명시되지 않음 | 설명 의미와 진단을 분리하고 schema/빈 설명은 전달 실패로 처리 | 해결 |
| D05 | usage 이상·다른 모델 반환·재실행 시의 동작이 문장 수준에 머묾 | 음수·비정수·잘못된 캐시 usage 거부, 모델 불일치 비용 미확정, 오류 후 중단, 기존 run 경로 재실행 거부 | 해결 |
| D06 | 익명 패킷에 무엇이 포함되는지 실행 전 확인 자료 없음 | 패킷 allowlist와 원본 연결 검사, 조건 키 별도 저장, 합성 시험 데이터를 실제 평가에서 거부 | 해결 |

**생성 프롬프트 두 개, 원문·질문, 18개 요청 payload, 평가 요구사항, 모델 설정, 반복 수와 진행 기준은 최초 초안과 동일하다.** 보완은 상태 표현·평가 전달 계약·실행 안전장치와 재현 코드에 한정했다. 최초 요청 미리보기와 최종 요청 미리보기의 byte 일치를 검사한다.

## 오프라인 검증

전용 실행기 시험은 11개 묶음으로 usage 이상, 전달 상태 구분, 동결 입력 변조 거부, 18슬롯 정상 처리, 거절 응답의 분모 유지, 통신 결과 미상, HTTP 오류, usage 누락, 모델 불일치, 요청 전 비용 한도, 실제 비용 초과를 확인했다. 각 실행 시나리오에서 재실행 거부와 출력 봉인 해시도 확인했다.

평가 패킷 시험은 7개 묶음으로 익명 18개·요구사항 54개, 전달 실패 구분, 원본 요청·응답·회계표 연결, 합성 실행 거부, 슬롯 교환·응답 변경·비용 변경 거부를 확인했다. 합성 응답은 임시 시험용이며 실험 응답이나 의미 성능 결과로 저장하지 않았다. 두 시험 모두 live API 호출 0회다.

[실행기 시험 결과](runtime_test_report.json), [평가 패킷 시험 결과](packet_test_report.json). 코드 검증은 실제 의미 타당도나 모델 성능 향상의 증명이 아니다.

## 받아들인 한계와 동결 범위

입력 길이·강조 횟수와 개입 내용의 효과를 완전히 분리하지 못한다. 점검 과정이 출력되지 않으므로 내부 수행을 관찰할 수 없다. 2~4문장·900 token 제한 때문에 복합 예외 설명이 압축될 수 있다. 세 사례는 이미 관찰한 오류를 바탕으로 고른 개발 사례이며, 두 AI도 사람 전문가 검증을 대체하지 않는다. 이 한계를 밝혀 개발 결과로만 해석한다는 조건에서 동결을 진행한다.

동결 대상은 1단계 18개 요청, 공통·추가 지시, 원문·평가 규칙, 비용·순서·진행 기준, 실행·익명 평가·검증 코드와 이 검토 근거다. 2단계 12개 새 조항은 후보·평가 gold·비용이 정해지지 않았으므로 실행 입력으로 동결하지 않는다. 이번 동결이 실제 API 생성이나 2단계 실행을 수행한 것으로 해석되어서는 안 된다.
